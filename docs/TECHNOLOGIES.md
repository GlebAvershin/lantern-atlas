# Lantern Atlas · технологии и инженерные решения

Lantern Atlas — головоломка на Godot 4.5.1 о передаче света между маяками. Восемь карт вводят дальние реле и закрытые станции. Игрок может получить оптимальную подсказку после любого допустимого хода. AI-инструменты использованы при производстве уровня, подготовке HUD, ревью сохранений и проверке игровой сборки. [Играть](https://glebavershin.github.io/lantern-atlas/) · [Видео](../evidence/nightwatch.mp4) · [Разбор Nightwatch](NIGHTWATCH.md)

## Как шлюз отвечает при отказе моделей

По сохранённой трассировке отключения и восстановления моделей в Kubernetes проверили восемь запросов. При потере основной модели шлюз завершил прерванный запрос через резервную. При отказе обеих моделей он отдавал готовый ответ из кеша, а для нового запроса вернул интервал повтора в 5 секунд. После восстановления повтор обслужила основная модель. Четыре чтения из кеша дали ноль новых токенов. В трассировке двух генераций учтены 358 токенов у резервной модели и 340 у основной. Действия сверили с семью решениями из сохранённого исследования и отдельно проверили чтение прогретого кеша основной модели.

Расчёт выполнил инструмент `aws___run_script` управляемого MCP-сервера AWS через Agent Toolkit for AWS в Codex. На момент запуска действовал план AWS Free. Сервис вернул успешный результат с нулём обращений к API ресурсов. [Результат и контрольные суммы](evidence/aws-toolkit.json) · [Расчёт и проверка](../studio/research/aws_audit.py) · [Как повторить](https://github.com/GlebAvershin/lantern-atlas/blob/main/studio/research/README.md#aws-agent-toolkit-replay)

## Что происходит с ревью уровня при отказе модели

Дизайнер отправляет варианты карты на проверку через <code>POST /review</code>. Если основная модель недоступна, шлюз передаёт тот же бриф запасной модели в пределах исходного 90-секундного срока. Запасная модель проходит тот же игровой MCP-валидатор. Ответ сообщает запрошенную и фактическую модели. Кеш принятого решения привязан к фактической модели, команде, брифу и ревизии. Клиент может закрепить модель через <code>allow_fallback: false</code>. [Маршрутизация](../studio/agents/gateway.py) · [Проверки ошибок и обратного маршрута](../studio/agents/test_failover.py)

| Сценарий в Kubernetes | Наблюдаемый ответ |
| --- | --- |
| Остановка Qwen во время генерации | SmolLM2 вернула проверенный вариант за 312 мс от начала запроса, HTTP 200 |
| Повтор на второй реплике во время отказа | Ответ SmolLM2 из кеша, 0 токенов новой генерации |
| Новый запрос с закреплённой недоступной Qwen | HTTP 502 |
| Обе модели остановлены | Новый бриф получил HTTP 503 с <code>Retry-After: 5</code>. Прежнее ревью прочитано из кеша |
| Qwen снова запущена | Та же задача получила новый ответ Qwen. Следующий запрос к другой реплике прочитал его из кеша |

В том же прогоне две команды выполнили 120 запросов десятью пакетами. Все 120 получили HTTP 200. Из них 12 потребовали генерации, 108 использовали кеш. У повторных запросов p95 составил 45,63 мс. Измерения относятся к тестовому кластеру и инструменту разработки уровней. [Облачный прогон](https://github.com/GlebAvershin/lantern-atlas/actions/runs/44811705071) · [Журнал отказа и восстановления](evidence/failover-live.json) · [Сценарий нагрузки](../studio/agents/mixed_probe.py)

Семь наблюдавшихся ответов из журнала повторно классифицированы в Databricks Free Edition и SQLite. Обе системы вернули одинаковые строки. Qwen3 Coder в AWS Bedrock выбрала ожидаемое действие в 7/7 случаев в обоих вариантах запроса. Это оценка классификации журнала. Само переключение выполняет код шлюза. Amplitude приняла семь событий QA, Sentry — одно предупреждение о контрольном случае полного отказа.

## Что делает облачный агент

Модель выбирает один из вариантов финала. MCP передаёт пару реле и маршрут независимому C++-решателю. Для приёмки нужно минимум пять ходов, причём отключение нажатий на реле должно удлинить решение или сделать его невозможным. Контрольная карта решается за два хода и отклоняется. Предложение можно проверить независимо от названия, объяснения или уверенности модели. ## Инфраструктура, доступ и наблюдаемость

Две реплики Python/FastAPI работают в Kubernetes (kind) на стандартном Ubuntu-раннере GitHub Actions. На этом же раннере llama.cpp обслуживает два отдельных CPU-маршрута — Qwen2.5-0.5B-Instruct и SmolLM2-360M-Instruct. Шлюз направляет запрос на выбранную модель, а отдельный процесс игры обслуживает MCP по stdio. Код платформы общий для трёх игр. В каждом репозитории есть собственный MCP-адаптер и workflow. [Workflow этой игры](../.github/workflows/game-agents.yml) · [Шлюз на проверенной ревизии](https://github.com/GlebAvershin/lantern-atlas/blob/4103603adde3dd325d511a2a2df66db834757f13/studio/agents/gateway.py) · [Kubernetes-манифест](https://github.com/GlebAvershin/lantern-atlas/blob/4103603adde3dd325d511a2a2df66db834757f13/studio/agents/deployment.yaml)

- **Контекст и качество.** При запуске реплика читает ресурс с брифом игры. Для задания допускается до четырёх вариантов, размер сериализованного брифа ограничен 8 КиБ. Вывод модели ограничен JSON-схемой. Принятие решения принадлежит игровому инструменту. При отказе агент передаёт причину модели и исключает этот вариант из следующей попытки. [Контракт проекта](../studio/agent_review.py)
- **Параллельные запросы и кеш.** В ключ входят игра, команда, ревизии игры и платформы, модель и отпечаток её весов, промпт и бриф. Транзакционная advisory-блокировка PostgreSQL 16 координирует запросы на разных репликах. Принимается только проверенный результат, срок действия — сутки. Ошибка до фиксации освобождает блокировку. Две тестовые команды используют отдельные bearer-токены. Запрос с неверным токеном получил 401.
- **Ревью и диагностика.** Ресурс MCP предоставляет информацию GitHub Actions о PR и ограниченный фрагмент кода из проверяемого git-коммита. Второй ресурс отдаёт записи SDK Sentry и Amplitude с локального приёмника на раннере. На контролируемый отказ записывается одно сообщение, на принятые решения — два события. Qwen получает фрагмент кода и отрицательный контроль и предлагает дополнительный тест. В ревью Qwen предложил проверить неизвестное имя карты. В коде есть явная ветка отказа, поэтому предложение уместно как дополнительный тест этой ветки. [Реализация](https://github.com/GlebAvershin/lantern-atlas/blob/4103603adde3dd325d511a2a2df66db834757f13/studio/agents/release_review.py) · [Ответ модели и данные SDK](evidence/cloud-review.json)

## Измеренный результат

[Модели согласились на Crescent Passage.](../studio/agent_review.py) Решатель подтвердил минимум в шесть ходов и невозможность решения без нажатия на реле. [Исходные запросы и ответы](evidence/cloud-review.json) · [Публичный прогон](https://github.com/GlebAvershin/lantern-atlas/actions/runs/44771390084)

| Серия одной тестовой команды | Клиентские запросы | Вызовы LLM | Токены inference | p95 у клиента |
| --- | ---: | ---: | ---: | ---: |
| Пустой кеш, обе модели уже загружены | 8 | 2 | 758 | 2411,6 мс |
| Повтор | 8 | 0 | 0 | 46,99 мс |
| После замены обоих pod | 8 | 0 | 0 | 49,61 мс |

В каждой серии четыре запроса направлены к каждой модели, трафик разделён между двумя репликами. В первой серии шесть запросов переиспользовали результаты соседних запросов. Та же задача для второй команды дала отдельный промах. После rolling restart проверены новые имена обоих pod и сохранность результатов для каждой команды. Таблица включает токены всех попыток **первой команды** для игрового задания. Отдельный обзор PR, контрольный запрос второй команды и подготовка инфраструктуры в неё не входят. На восьми запросах p95 по методу ближайшего ранга совпадает с максимумом. Это короткий функциональный нагрузочный тест.

**Как повторить.** В разделе Actions этого репозитория выбрать *Game review agents → Run workflow → main*. Стандартный раннер поднимет временный кластер и PostgreSQL, загрузит веса с проверкой SHA-256 и сохранит артефакт `game-agent-evidence`. В нём есть ответы до и после перезапуска, события SDK и текст ревью. Прогон работает также при открытии PR. Постоянный сервис и платный аккаунт модели для проверки не требуются. [Сценарий нагрузки](https://github.com/GlebAvershin/lantern-atlas/blob/4103603adde3dd325d511a2a2df66db834757f13/studio/agents/probe.py) · [Запуск и остановка кластера](https://github.com/GlebAvershin/lantern-atlas/blob/4103603adde3dd325d511a2a2df66db834757f13/studio/agents/cloud.sh)

## Проверка через подписки разработчика

Каждая модель выбрала финал из трёх вариантов. C++-решатель отдельно проверил длину решения и необходимость дальнего реле. Один и тот же MCP-бриф передан Codex CLI через вход ChatGPT и Gemini через Google Antigravity CLI. Обе команды запущены на Mac. Инференс выполняли сервисы провайдеров.

| Маршрут | Запрошенная модель | Выбор | Вердикт игрового инструмента |
| --- | --- | --- | --- |
| Codex | gpt-6.2-sol | `crescent_passage` | Принято |
| Google Antigravity | gemini-3.8-flash-low | `crescent_passage` | Принято |

В протоколе сохранены обоснования моделей, версия исходников, хеш брифа и независимые вердикты. Это по одному завершённому решению на маршрут. Скрипт использует локальные сеансы CLI, для Gemini отключает расход дополнительных AI-кредитов и передаёт ответы существующему MCP-инструменту. Облачный нагрузочный тест выше использует отдельные серверы Qwen и SmolLM2. [Протокол](evidence/subscription-review.json) · [Скрипт](https://github.com/GlebAvershin/lantern-atlas/blob/main/studio/agents/subscription_review.py) · [Вход ChatGPT](https://learn.chatgpt.com/docs/auth) · [Вход Google](https://antigravity.google/docs/install)

Для повторения из корня этого репозитория используйте Python-окружение проекта Lantern Atlas (`uv sync --project studio --locked --python 3.12` из его корня). После входа в официальные CLI выполните:

```sh

"$platform/studio/.venv/bin/python" "$platform/studio/agents/subscription_review.py" --game atlas --game-root . --provider gemini
```

## Исходный замер до автоматического переключения

В исходной версии шлюза на временном Linux-раннере две команды одновременно проверяли три разных набора карт через Qwen и SmolLM2. Один пакет содержит 12 сочетаний «команда × модель × набор карт». Каждый пакет направлялся на две реплики шлюза. После первого пакета сценарий повторил задания ещё девять раз, меняя порядок и чередуя реплики. Веса к началу замера уже находились в памяти.

| Серия | Ответы 200 | Промахи / попадания | Токены | p95 у клиента |
| --- | ---: | ---: | ---: | ---: |
| Первые запросы | 12/12 | 12 / 0 | 5 934 | 5 266 мс |
| Повторные запросы | 108/108 | 0 / 108 | 0 | 46 мс |

Затем тест отправил новую задачу и дождался, когда llama.cpp показал занятый слот. Процесс Qwen был остановлен во время вычисления. Шлюз вернул 502 для прерванного запроса и для нового запроса к недоступной модели. Пока Qwen был остановлен, ранее принятый ответ Qwen пришёл из кеша, а SmolLM2 обработала новую задачу. После перезапуска Qwen повтор исходного запроса вызвал новую генерацию, а запрос через другую реплику попал в кеш. Это проверка изоляции отказа и восстановления по повтору клиента. Нагрузка ограничена одним кластером, двумя командами и десятью короткими сериями.
